# PR を出す前

PR の本文は、作業指示者がマージを決める材料です。本文と事実が食い違うと、確かめていないものが出荷されます。作業指示者が気づいて止めたとしても、それは本文が役目を果たしたことにはなりません。この手順は、このリポジトリの PR で実際に起きた食い違いから作っています。

## 範囲

振る舞いか構造を変えた PR では、下の手順をすべて行います。意味を変えない文言の整理、ファイルの移動、記録だけの PR では、`bun test` と `bun run check` を通し、差分を自分で確かめれば足ります。どちらでも、「確認できなかったこと」の書き方は同じです。

## 手順

```
- [ ] 1. 変更とテストを終える
- [ ] 2. bun run pre-pr を走らせ、捕まえていない変異をテストで捕まえる
- [ ] 3. simplify とレビューをかけ、指摘に対応する
- [ ] 4. 最後のコミットで bun run pre-pr を走らせ、下書きを得る
- [ ] 5. 下書きの（）を埋め、「確認できなかったこと」を書く
- [ ] 6. bun run pr-body <本文のファイル> を通してから、PR を作る
```

**`bun run pre-pr`。** テスト、検査、ミューテーションを走らせ、PR 本文の「確認」の下書きを標準出力に出します（30 秒ほど）。e2e は走らせず、挙げるだけです。下書きの数と区分は、そのまま使ってください。#92 では、ミューテーションの出力を読んで数を書き写し、外れた変異を数え落としました。その結果、「テストが届かないものは 0 個」と書いていました。下書きのコメントには、走らせたコミットが入ります。コメントを残してください。`bun run pr-body` と CI は、下書きのあとに文書（`*.md`、`docs/`）以外のファイルが変わっていると失敗します。そのときは、最後のコミットで走らせ直し、コメントだけでなく「確認」を更新します。文書だけを直したときは、取り直さなくて構いません。

**simplify とレビュー。** 2 で足したテストも含めて、最後の変更のあとにかけます。かけたあとに振る舞いや構造を変えたら、3 からやり直します。#91 と #92 では、かけたあとに変更を足し（#92 では新しいモジュールを含む）、かけ直さずに完了と報告しました。

**下書きを埋める。**

- **捕まえていない変異**：状態と区分によらず、すべてについて、テストで捕まえるか、捕まえない理由を書きます（ADR 0021）。
- **e2e**：挙げられたものを走らせ、結果を書きます（ADR 0023）。モデルは Haiku で足ります（`ANTHROPIC_MODEL=haiku`）。
- **確認の手段**：何で確かめたか（実際のハーネス、モック、単体テスト）を項目ごとに分けて書きます。e2e の外部サービスはモックです。
- 下書きや本文をファイルに置いたら（`.local/` の中）、PR を作ったあとに消します。

## 「確認できなかったこと」

作業指示者は、ここに書いたものを、自分で確かめるか、リスクとして受け入れるかを決めます。確かめられたものをここに書くと、その判断をさせることになり、テストの穴も隠れます。

項目ごとに、区分、確かめる手段、費用の見積もり（時間、実費）、確かめなかった理由を書きます。区分は次の 3 つだけで、`bun run pr-body` と CI が、区分のない項目を落とします。

- **`区分：実サービス`**：実際のチャットサービス、アカウント、課金（LINE の Push の通数、API の料金）が必要。
- **`区分：手段なし`**：手元に手段がない。何がないかを書きます。偽の ACP エージェント（`test/fixtures/acp-agent.ts`）、偽のコネクター、API のモック、実際のハーネスとモックの組み合わせで起こせないかを、先に考えます。
- **`区分：承認 名前`**：作業指示者が、確かめずに出すこと、または別に扱うことを承認した。どこで扱うかを書きます。

手元で、実際のハーネス（`ANTHROPIC_MODEL=haiku`）とモックや偽物で確かめられるものは、どれにも当たりません。確かめて「確認」に書きます。

- 契約の利用枠、数十分までの時間、確かめる価値の判断（「安全境界ではない」など）は、理由になりません。e2e の中核の基準は、毎回走らせるものの基準で、その PR を確かめるかの基準ではありません。
- それでも省くなら、PR を出す前に、手段と費用を示して作業指示者に聞きます。
- 確かめた範囲の残り（試していないモデル、回数、場面）は、「確認」の断り書きにせず、ここの項目にします。変更の意図（issue と作業指示者の言葉）にある場面を覆っているかも、ここで言います。

例：#106 では、「Haiku とモックの LINE で 5 分」と書いたうえで、「安全境界でも節約の仕組みでもない」として、新しい案内の効き目を確かめずに出しました。5 分で確かめると、意図した問いかけに黙るようになっていました（#107）。#78 では「偽のコネクターでは起こせない」と書きましたが、`roomName` を差し替えれば起こせ、その間テストの穴が隠れていました。

## 出したあと

本文の誤りに気づいたら、マージの後でも直します。消さずに「（訂正 YYYY-MM-DD）」として、何が誤りだったかを残します。

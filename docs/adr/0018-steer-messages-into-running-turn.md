# 作業中に届いた発言は、ハーネスが対応していれば、そのターンに差し込む

中継は、エージェントの作業中（`session/prompt` が返る前）に届いた発言をためておき、ターンが終わってから 1 回でまとめて渡していました。そのため、依頼の直後に補足や訂正を送っても、最初のターンは元の依頼のまま最後まで進み、補足を読むのは返事が出たあとでした。チャットでは、送ってから付け足す使い方が多いです（#39）。2026-11-17 に決めました。

## 分かったこと

ACP v1 の仕様では、1 つのターンは 1 回の `session/prompt` です。作業中のターンに発言を足す標準の方法はありません。

標準化の前の拡張として、`_session/steering` があります。

- **宣言**：ハーネスは、`initialize` の応答の最上位の `_meta` に `steering: { supported: true }` を書いて、この拡張に対応していることを示します。
- **実装**：`claude-agent-acp`（0.101.0 のソースで確認）と `codex-acp` が実装しています。OpenCode は、PR が出ている段階です。
- **標準化**：ACP の PR #1261 で、v2 の `session/prompt` に `delivery: "steer" | "queue"` を足すことが提案されています（2026-11-17 時点で open）。
- `codex-acp` と OpenCode の状況は、検索結果で見ただけで、ソースでは確かめていません。

`claude-agent-acp` 0.101.0 の `steer()`（`src/acp-agent.ts`）は、次のように動きます。

- **作業中なら**、発言をそのターンに差し込み、`injected` を返します。
  - 優先度は、ふつうは `now` です。生成の途中なら、その生成（モデルの 1 回の応答）を打ち切って差し込んだ発言を読み、ツールの実行中なら、そのツールを裏に回します。打ち切るのは 1 回の応答だけで、ターンと会話はそのまま続きます。
  - 実行承認の返事を待っている間は、優先度が `later` になります。承認の依頼は取り消されず、返事が出たあとに渡されます。
  - 差し込んだ発言への応答が出るまで、元の `session/prompt` は返りません。
- **作業中でなければ**、既定では、ハーネスが自分で新しいターンを始め、`startedNewTurn` を返します。
  - その場合、中継はそのターンの終わりを知ることができません。
  - 要求の `_meta` に `steering: { idleBehavior: "promptRequired" }` を付けると、何もせずに `promptRequired` を返します。発言は中継の手元に残ります。
- 作業中に 2 つ目の `session/prompt` を送った場合は、前のターンの後ろに並びます。差し込まれはしません。
- ACP v2 の側では、この拡張を出していません（`src/v2/initialize.ts`）。

実機（2026-11-17、Claude Code 2.1.325、モックの LINE）では、次のことを確かめました。

- ファイルを順に読んでいる最中に送った 2 通目（「返信の最後に『追記OK』と付けて」）が差し込まれ、1 通目への返信に反映されました。返信は 1 通で、重複はありませんでした。
- 長い文章を書かせている途中で差し込むと、書きかけの文章（642 字）は、打ち切られたまま会話の履歴に残りました。エージェントは、最初から書き直さずに続きから書き、差し込んだ依頼にも応えました（Claude Code の会話ログで確認）。思考（thinking）は会話ログに中身が残っておらず、引き継がれるかは確かめられていません。
- 実行承認の返事を待っている間に送った 2 通目も、差し込まれました。承認の依頼は取り消されず、承認できました。
  - 2 通目がエージェントに渡ったのは、エージェントが最初の報告を送ったあとでした。エージェントは、2 通目に合わせた報告を、もう 1 通送りました。

## 決めたこと

- ハーネスが `_session/steering` を宣言していれば、作業中に届いた発言をそのターンに差し込む。宣言していなければ、今までどおりためておき、ターンが終わってからまとめて渡す。
- 差し込むのは、中継がセッションに渡す発言すべて。メンションのない発言に限ることも、ルームごとに選べるようにすることもしない。公式の Discord プラグインと同じ。
- 差し込むときは、必ず `idleBehavior: "promptRequired"` を付ける。ハーネスが自分でターンを始めると、中継がターンの終わりを知れず、次の発言を渡す時期を決められないため。
- 発言を失わない。
  - `injected` が返らなかったら、渡していないものとして扱う。`promptRequired` が返った場合も、要求が失敗した場合も同じ。
  - 渡していない発言は、あとから届いた発言より前に、次のターンで渡す。
  - 要求が失敗したり、想定外の結果が返ったりしたら、以後は差し込みを使わない。
- 差し込みは 1 回ずつ順に送る。差し込む時点でたまっている発言は、1 回にまとめる。
- ACP v2 へは、v2 に steering の標準の方法（PR #1261 の `delivery: "steer"` など）ができてから移る。そのとき、この差し込みを置き換える。

## Considered Options

- **作業を止めて、渡し直す。** ACP 標準の `session/cancel` でターンを止め、ためた発言と合わせて `session/prompt` で渡し直す。標準の範囲で済む。ただし、途中までの作業が捨てられるか、書きかけのまま残る。実行承認の返事を待っている間に止めると、送った承認の依頼（ADR 0014 の束）の後始末も必要になる。
- **ACP v2 の標準化を待つ。** 拡張に頼らずに済む。ただし、いつ決まるか分からない。
- **メンションと DM だけを差し込む。** 受信モードが「すべて」のルームの雑談で、作業が中断されなくなる。ただし、メンションを付けずに送った補足は、次のターンに回る。

## Consequences

- 拡張に頼りますが、宣言しているときにだけ使い、宣言がなければ、ためておく動きに戻ります。複数のハーネスが同じ形で実装している拡張なので、特定のハーネスに固有の機能に頼らないという方針（ADR 0006）とは食い違わないと判断しました。
- 受信モードが「すべて」のルームでは、雑談でも作業が中断されます。差し込まれた発言を、エージェントがそのたびに読むためです。途中までの作業は残るので、失うのはおもに、そのたびに発言を読んで判断する手間と、作業の流れです。中断が多すぎるようなら、差し込む発言を絞るか、少し待ってまとめるかを、あらためて決めます。
- 実行承認の返事を待っている間に送った訂正は、エージェントがその次の動作（返信など）を済ませたあとに渡ることがあります。
- 1 つのターンに、あとから別の人や別のルームの発言が加わります。承認の依頼が誰の発言から出たものかは、さらに決めにくくなります（#29）。
- ターンが終わる直前に差し込もうとして `promptRequired` が返る場合は、テストで確かめました（偽のセッション）。実機では再現できていません。

# 同時に届いた実行承認の依頼は、1 通の承認依頼の束にまとめる

> 1 つの束を 5 つまでにしても、「常に許可」の範囲が長いと、文面が Discord の上限に収まりませんでした（#46）。今は、文面が承認者のいるサービスの本文の上限を超えるとき、その手前で束を分けます。下の「文面を Discord の上限に収めるため」は、件数の上限だけでは成り立ちません。

ハーネスが同時に複数のツールを呼ぶと、実行承認の依頼が同時に届きます。中継は、依頼ごとに 1 通を承認者の DM に送っていました。承認者は、届いた数だけ答える必要があり、答えていない依頼が残ると、エージェントのターンが止まったままになります（#23）。LINE では、ボタン（quickReply）があとから届いた発言で消えるので、最後の 1 通にしかボタンが残りません。

Claude Code（claude-agent-acp 0.101.0）で確かめると、読み取り専用の MCP ツールを並列に 3 つ呼んだとき、依頼は約 0.6 秒のあいだに 3 通届きました。Bash の書き込みを並列に呼んだときは、前の依頼に答えるまで次の依頼は届きませんでした（2026-11-16）。

## 決めたこと

- 中核が、同時に届いた依頼を承認依頼の束にまとめ、1 通で送る。最後の依頼から 1 秒、次の依頼が来なければ送る。依頼が続いても、最初の依頼から 3 秒で送る。1 つの束には 5 つまで入れる（文面を Discord の上限に収めるため）。
- 束には ID を付け、コネクターには今までの依頼と同じ形（`sendApproval(user, text, id)`）で渡す。依頼が 1 つの束は、今までと同じ文面にする。
- ボタンと束の ID での答えは、その束に残っている依頼すべてに当てる。あとから届いた依頼は別の束にするので、承認者が見ていない依頼には当たらない。束の中の依頼にもそれぞれ ID を付け、文字で 1 つずつ答えられるようにする。
- 答えを受け付けたあと、答えていない束が残っていれば、いちばん古い束を、残りの件数を添えて、答えた人に送り直す。送り直す時点で答えの済んだ依頼は、文面から外す。
- ID のない `yes`・`no` は受け付けない。DM の雑談の「yes」が承認になる余地を作らない。
- 依頼者のいるルームに「承認待ち」を表示することはしない。

## Considered Options

- **依頼ごとに送ったまま、答えたあとに残りを送り直すだけにする。** 中核の変更は小さい。ただし、承認者は依頼の数だけ答える必要があり、LINE では Push も依頼の数だけ使う。
- **束の中の依頼ごとに、ボタンを付ける。** 1 通の中で選び分けられる。ただし、LINE の quickReply と Discord のボタンの数の上限に当たりやすく、文字で答えれば足りる。
- **未回答の依頼が 1 つだけのとき、ID のない `yes` を受け付ける。** 依頼が 1 つの場合は手軽になる。ただし、DM の雑談の「yes」が承認になりうる。束にすれば、依頼が 1 つの場合もボタンで答えられる。
- **依頼者のいるルームに「承認待ち」と表示する。** 止まっている理由が依頼者に分かる。ただし、LINE のグループでは、返事に使う Reply トークンを使うか、Push の通数を使う（ADR 0012 で却下した、文章での受け取りの合図と同じ問題）。

## Consequences

- 承認の依頼が届くまでに、最大 3 秒（ふつうは 1 秒）の遅れが加わります。
- LINE の Push は、依頼の数ではなく束の数だけ使います。送り直しにも Push を使いますが、送り直しが起きるのは、前の束に答える前に、3 秒以上遅れて次の依頼が届いた場合だけです。
- 「常に許可」（ACP の `allow_always`）を承認者が選べるようにする変更は、別に決めます（#23）。束の中の依頼は、依頼ごとに答えを持てる形にしてあります。

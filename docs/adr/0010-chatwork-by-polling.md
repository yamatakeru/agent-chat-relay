# Chatwork の発言は、API のポーリングで受信する

Chatwork のコネクターは、Webhook を使わず、REST API を数秒ごとに呼び出して新しい発言を受信します（2026-11-09）。

Chatwork の Webhook には、次の制約があります。

- 設定できるのは、1 アカウントあたり 5 件まで。
- 「自分へのメンション」なら、1 件ですべてのルームの分を受信できる。しかし、メンションのない発言と DM を受信するには、ルームごとに Webhook を 1 件ずつ、画面から手作業で作成する必要がある。
- 配信に失敗しても再送されない。

この中継では、エージェントが読めるように、登録したルームのメンションのない発言も記録します。また、実行承認の返事は DM で受け取ります。Webhook では、これらを合わせて 4 ルームまでしか扱えません。

既存のアダプターも、2 つの方式に分かれています。Webhook 型（Vercel の Chat SDK 用の chat-adapter-chatwork など）は、メンションに応答する Bot として作られています。すべての発言を扱うもの（MulmoBridge の @mulmobridge/chatwork、hubot-chatwork）は、ポーリングを使っています。

## 決めたこと

- 5 秒ごとにルーム一覧（`GET /rooms`）を取得し、`last_update_time` が進んだルームだけ、前回からの差分（`GET /rooms/{id}/messages?force=0`）を取得する。同じ秒に届いた発言を取りこぼさないように、更新時刻が同じでも、もう一度だけ取得する。
- 起動時のルームの状態を起点にし、それ以前の発言は取得しない。あとから差分として届いた起動前の発言は、登録したルームのものなら記録だけして、エージェントには渡さない。
- 起動後にルーム一覧に現れたグループチャットは、Bot が追加されたものとみなし、ペアリングのコードを投稿する（LINE の join イベントに相当）。
- Bot は、専用の Chatwork アカウントの API トークンで発言する。

## Considered Options

- **Webhook。** すぐに届く。ただし、上の 5 件の制約により、扱えるルームが 4 つまでになる。トンネルも必要になる。停止中の発言は再送されずに失われる。
- **併用**（メンションは Webhook で受信し、それ以外はポーリング）。返信は速くなるが、仕組みが 2 つになる。ポーリングの遅さが問題になったら、あとから追加すればよい。

## Consequences

- 公開 URL もトンネルも不要です。Chatwork だけで使う場合、`scripts/relay.sh line-tunnel` は不要になります。
- 返信は、最大でポーリングの間隔（既定 5 秒、`RELAY_CHATWORK_POLL_SEC` で変更可）だけ遅れます。
- API の回数制限（5 分に 300 回）を、取得と送信で分け合います。取得は、5 秒ごとに 1 回と、更新のあったルームごとに 2 回です。制限に達したら、解除されるまで取得を止め、送信はエラーとしてエージェントに伝えます。
- `force=0` の差分の起点は、API トークンごとに Chatwork 側で保持されています。同じトークンを、ほかのプログラムでの取得に使わないでください。

# Chatwork の発言は、API の定期取得で受け取る

Chatwork の接続部は、Webhook を使わず、REST API を数秒ごとに呼んで新しい発言を受け取る（2026-11-09）。

Chatwork の Webhook には、次の制約がある。

- 設定は、1 アカウントあたり 5 件まで。
- 「自分へのメンション」なら 1 件で全ルームの分を受け取れる。メンションのない発言と DM を受け取るには、ルームごとに Webhook を 1 件ずつ、画面から手で作る必要がある。
- 失敗しても再送されない。

この中継では、エージェントが読めるよう、登録したルームのメンションのない発言も記録する。また、実行承認の返事は DM で受ける。Webhook では、これらを合わせて 4 ルームまでしか扱えない。

既存のアダプターも、2 つの作りに分かれる。Webhook 型（Vercel の Chat SDK 用の chat-adapter-chatwork など）は、メンションに応える Bot として作られている。全発言を扱うもの（MulmoBridge の @mulmobridge/chatwork、hubot-chatwork）は、定期取得を使っている。

## 決めたこと

- 5 秒ごとにルーム一覧（`GET /rooms`）を取り、`last_update_time` が進んだルームだけ、前回からの差分（`GET /rooms/{id}/messages?force=0`）を取る。同じ秒に届いた発言を取りこぼさないよう、同じ更新時刻でもう一度だけ取る。
- 起動したときのルームの状態を起点にし、それまでの発言は取りに行かない。あとで差分として届いた、起動前の発言は、登録したルームなら記録だけして、エージェントには渡さない。
- 起動後にルーム一覧に現れたグループチャットは、Bot が追加されたものとみなし、ペアリングのコードを投稿する（LINE の join に当たる）。
- Bot は、専用の Chatwork アカウントの API トークンで発言する。

## Considered Options

- **Webhook。** すぐ届く。ただ、上の 5 件の制約で、扱えるルームが 4 つまでになる。トンネルが要る。止まっている間の発言は、再送されずに失われる。
- **併用**（メンションは Webhook で受け、それ以外は定期取得）。返事は速いが、仕組みが 2 つになる。定期取得で遅さが問題になったら、足せばよい。

## Consequences

- 公開 URL もトンネルも要らない。Chatwork だけで使うなら、`scripts/relay.sh tunnel` は不要になる。
- 返事は、最大で取得の間隔（既定 5 秒、`RELAY_CHATWORK_POLL_SEC`）だけ遅れる。
- API の回数制限（5 分に 300 回）を、取得と送信で分け合う。取得は 5 秒ごとに 1 回と、更新のあったルームごとに 2 回。制限に達したら、解除されるまで取得を止め、送信はエラーにしてエージェントに伝える。
- `force=0` の差分は、API トークンごとに Chatwork が覚えている。同じトークンを、ほかのプログラムの取得に使わない。

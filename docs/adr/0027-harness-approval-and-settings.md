# pi と OpenCode では、既定で中継の実行承認を使い、明示したときだけ端末の設定を引き継ぐ

pi と OpenCode では、実行承認の仕組みも、端末やプロジェクトの設定の読み込み方も異なります（[#63](https://github.com/yamatakeru/agent-chat-relay/issues/63)）。初回対応では、承認者がルームからの実行を判断できる既定と、管理者が普段の環境を使うための明示指定を分けます。Claude Code の現行動作は変更しません。ハーネス間で残る違いをどこまで揃えるかは、初回対応の範囲に含めず、別途検討します。

## 分かったこと

2026-11-20 に、pi 1.5.2 と pi-acp 0.0.34 の試作、OpenCode v2.3.2 で、新規・再開後の `reply` と非チャット操作の実行承認を確かめました。ハーネスと中継の MCP は実物、モデルとチャットサービスはモックです。試験は分離した設定・状態で行い、端末の設定や許可は持ち込んでいません（[#70 の検証記録](https://github.com/yamatakeru/agent-chat-relay/issues/70#issuecomment-7035523222)）。以下は正式対応で実現する方針であり、試作で確認した範囲とは区別します。

## 既定の実行承認

- 中継が渡すチャット用ツールと、実際の読み取り先が作業ディレクトリ内に収まると確認できる読み取り専用の操作は、承認なしで使えます。範囲外や範囲を確認できない読み取り、編集、シェル、その他のツールの実行は、実行前に承認を求めます。中のファイルはすでに `reply` で添付できるため、読み取りだけを承認対象にしてもルームに出せる範囲は狭まりません（[ADR 0008](0008-chat-tools-without-approval.md)、[ADR 0009](0009-returned-files-from-workspace-without-approval.md)）。
- 承認依頼には操作と対象を示し、「今回だけ許可」と「拒否」だけを出します。拒否・期限切れ・切断では実行せず、遅れて届いた許可も使いません。「常に許可」は、範囲と保存先がハーネスによって異なるため初回は出しません。オートモードは採りません（[ADR 0016](0016-no-auto-mode.md)）。
- OpenCode ではチャット用ツールを直接公開し、`full_codemode` は初回の対象外にします。比較試験では、`full_codemode` 内の編集は編集として識別できず、外側の `execute` の承認依頼として届きました（[#70 の検証記録](https://github.com/yamatakeru/agent-chat-relay/issues/70#issuecomment-7035523222)）。

## 作業ディレクトリと設定の継承

- 既存の `--workspace` / `RELAY_WORKSPACE` で管理者の作業ディレクトリを指定できます。専用の作業ディレクトリと同じく、中のファイルは承認なしで読み取ってルームに返せます。管理者は、ルームへ出してよい場所を指定します。指定するだけではハーネスの設定は引き継ぎません。
- 既定では端末やプロジェクトのハーネス設定を引き継ぎません。`--harness-settings default` / `RELAY_HARNESS_SETTINGS=default` を明示したときだけ、管理者が信頼する環境の設定を引き継ぎます（[ADR 0017](0017-admin-chooses-workspace-and-harness-settings.md)）。この指定では、既存の allow ルールや hooks、拡張・プラグインによって、中継の実行承認を通らない操作がありえます。中継はこの指定でも自分の承認の仕組みを組み込み、既定で承認不要とする操作の範囲を自らは広げません。オートモードも選びません。ただし、引き継いだ設定が判断を変えたり、拡張・プラグインが起動時にコードを実行したりするため、既定と同じ承認を保証できないことを文書と起動時の両方で警告します。
- 設定を継承しない起動では、管理者が中継用のモデルと認証を明示して用意します。ハーネスの標準ログインを使う場合も、資格情報と状態は作業ディレクトリ外の中継専用領域に置き、端末の設定・状態を丸ごと共有しません。認証情報はルームへの出力、ログ、コマンド引数に載せません。
- 対象バージョンの pi と OpenCode では、Claude Code と同等の自動メモリを確認できていません。`--harness-memory` / `RELAY_HARNESS_MEMORY=1` は初回は未対応とし、指定があれば理由を示して起動しません。会話履歴の保存や既存の指示ファイルの読み込みで代用しません。
- OpenCode の既存の `opencode.json` や `opencode.jsonc` を、中継は上書きも削除もしません。中継が設定ファイルを生成する必要があるなら、作業ディレクトリの外にある中継の管理領域に置きます（[#76](https://github.com/yamatakeru/agent-chat-relay/issues/76)）。配置だけでは設定の優先順位は保証されないので、実際に読み込まれる設定を確かめます。

## pi の ACP アダプター

初回は、固定バージョンの pi-acp に対するパッチと中継管理の pi 拡張を、このリポジトリで管理・同梱します。中継本体とハーネスの間の接続は ACP・MCP のままです。上流の取り込みを初回対応の前提にしない代わりに、パッチの保守・配布と、上流の更新時の検証を中継側で担います。上流への提案や固定した fork への移行は別途検討します。

## 起動と再開

`--session-id` で再開できるのは、同じハーネス・同じ作業ディレクトリで中継が作ったセッションだけです。中継は、ハーネス・作業ディレクトリの実パス・セッション ID の組を作業ディレクトリの外に記録します。ハーネスの一覧に ID があるだけでは再開を許しません。再開時は現在の起動設定を適用し、以前の実行承認を暗黙に引き継ぎません。

起動・再開時に、中継が必要とする承認経路や、その起動方法で適用すべき設定を確認できなければ開始しません。ただし、設定の継承を明示した場合は、引き継いだ設定が個々の操作で承認を省くことまで中継は防ぎません。

## 正式対応の条件

試作では次を確認していません。正式対応の前に、実際のハーネスで確かめます。既定の方針を守れない構成では起動させません。

- 管理者が指定した作業ディレクトリでも、実際の読み取り先で範囲を判断できること。外を指すリンクや読み取り先が不明な操作では、承認なしで結果を返さないこと。
- 既定でユーザー・プロジェクト・上位ディレクトリ等から設定や指示、実行可能な拡張が持ち込まれず、保存済みの許可も効かないこと。pi では指示・設定の別の読み込み経路とアダプター側の探索、OpenCode ではプロジェクト設定と独立した指示探索や管理設定、プロジェクト単位の許可の保存も確かめます。
- 有効なすべてのツール実行経路で既定の承認が効くこと。OpenCode の試験は `build` に限るため、他のエージェントやサブエージェントも、使えるようにするなら確認します。pi の試作の承認依頼は ACP 上で `kind: other` なので、分類値だけに頼らず操作と対象を表示できることを確認します。
- 期限切れや切断後に許可が届いても実行しないこと。pi 側の承認待ちの期限と、中継の期限（現在は30分）も合わせて確認します。

## Considered Options

- **中の読み取りも毎回承認する。** 操作は単純になるが、同じファイルをチャットに添付できるので、ルームへ出せる範囲は変わらず、確認の回数が増えます。
- **設定を継承しない、指示だけに限定する、または承認と衝突したら起動を拒む。** 承認の前提は維持しやすい一方、管理者は普段使う設定や拡張を使えません。既定では継承せず、明示指定だけで管理者に判断を任せます。
- **「常に許可」や端末のセッションも初回から使えるようにする。** ハーネスによる許可の範囲・保存先の違いや、端末の会話を持ち込む影響を別途扱う必要があります。
- **OpenCode の起動設定を作業ディレクトリ内に書く。** 中継の設定の書き込みと管理者のプロジェクト設定を分離できず、設定の優先順位も解決しません。

## Consequences

- [ADR 0015](0015-allow-always-by-approver.md) と異なり、OpenCode が ACP で `allow_always` を示しても、中継は初回対応の範囲でこの選択肢を出さず、選びません。Claude Code の扱いは変えません。
- [ADR 0017](0017-admin-chooses-workspace-and-harness-settings.md) と異なり、pi と OpenCode では、作業ディレクトリが同じでも端末で作ったセッションは再開しません。

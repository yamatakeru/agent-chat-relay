# サービスによって使えない操作は、ツールの説明に書き、使えるサービスがなければツールを出さない

チャット用ツールの `react` と `edit_message` は、使えるチャットサービスが限られます。過去の発言を読めるかどうか（`fetch_messages`）も、サービスによって違います。しかし、どのサービスで使えるかは、エージェントに伝わっていませんでした。LINE のトークで、エージェントが `react` を呼んで失敗し、文章で送り直したことがあります（#28）。

使えるかどうかは、クライアント（ハーネス）ではなく、ルーム（`chat_id` の先頭のサービス）で決まります。1 つのセッションに、複数のサービスのルームが混ざります。MCP では、ツールの一覧をクライアントごとに変えられますが、引数の値によって使えるかどうかが変わることを表す仕組みはありません（2026-11-16）。

## 決めたこと

- どのサービスで使えるかは、コネクターがその操作のメソッド（`react`・`edit`・`history`）を実装しているかで決める。コネクターに、別の申告は足さない。判定は `Relay.servicesFor` の 1 か所にまとめ、次の 3 つは、どれもこの判定から作る。
  - ツールの説明：使えないサービスがあれば、使えるサービスを書く（例：「使えるのは Discord（discord:） のルームだけ」）。`fetch_messages` には、中継が起動してからの分しか読めないサービスを書く。
  - ツールを出すかどうか：使えるサービスが 1 つもなければ、`react` と `edit_message` を出さない。`fetch_messages` は、どのサービスでも動くので出す。
  - エラー：使えないサービスで呼ばれたら、使えるサービスと代わりの手段を書いたエラーを返す（`isError`）。ツールの説明を読まずに呼ぶエージェントのための受け皿にする。
- つながるコネクターは起動時に決まるので、ツールの一覧も起動のあいだは変わらない。

## Considered Options

- **案内（MCP の `instructions` と最初のプロンプト）に、サービスごとに使える操作を書く。** 1 か所で全体を伝えられる。ただし、ツールの説明と内容が重なる。案内には、複数のツールにまたがる関係や制約を書くのがよいとされている。また、案内をどう使うかはホストしだいで、モデルに届くとは限らない。ツールの定義を必要になったときに読み込むホストでは、ツールを選ぶ時点で見えるのはツールの説明のほう。
- **`chat_id` の入力スキーマに、`^discord:` のような `pattern` を付ける。** 制約を、機械が読める形で表せる。ただし、入力検証の失敗は、SDK によっては JSON-RPC のエラーになり、ホストがモデルに渡さないことがある。エラーの文面も正規表現の不一致になり、直し方が分かりにくい。`pattern` を無視したり受け付けなかったりするハーネスやモデルもありうる。
- **サービスごとに別のツールにする（`discord_react` など）。** 使えるかどうかがツールの名前で分かる。ただし、サービスが増えるとツールも増え、ルームを問わない 1 組のチャット用ツールという形が崩れる。

## Consequences

- LINE だけの構成では、`react` と `edit_message` が出ません。
- 省略できる操作をコネクターに足すときは、`OptionalOperation` に加え、説明とエラーを `servicesFor` から作ります。
- 説明の文面でエージェントの選択が変わるかは、モデルによります。複数のサービスをつないだ構成でも、使えないサービスで呼んだときはエラーで直せます。

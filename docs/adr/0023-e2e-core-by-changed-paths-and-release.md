# e2e は中核だけを既定にし、変更したパスとリリースを契機に走らせる。判定はスクリプトにさせる

e2e（`test/e2e/*.sh`）は、実際のハーネスを動かすので、1 回が分単位で、契約の利用枠を使います。0.1.1 の作業で測ると、検証にかかった時間の大半は e2e でした。そのうえ、各手順の成否は人が出力を読んで判定していました。安全を保ったまま、イテレーションを速くするために、e2e の範囲、走らせる契機、判定の仕方を決めました（#88）。2026-11-20 に決めました。

## 分かったこと

**かかった時間**（0.1.1 の作業。中継のログと fallow の出力から）

- `line.sh` を 3 回、約 16 分。そのうち約 10 分は、画像の手順の待ち時間でした。Haiku が別のルームを見て画像を見つけられず、画像が返るまで待つループ（最大 200 秒）を毎回使い切りました。
- 3 回のうち 2 回は、手順の組み立ての誤りを直すための試行でした。
- ミューテーションは、規則どおりの差分では数秒〜数十秒でした。約 8 分かかったのは、テストだけの PR で、ファイル全体にかけた分です。

**e2e でしか確かめられないこと**

各手順を、同じ中継の振る舞いを確かめる単体テスト（`test/relay.test.ts`）と突き合わせました。中継の側の振る舞いには、どの手順にも単体テストがあります。e2e でしか確かめられないものは、次の 2 種類でした。

- **ハーネスとの結合。** 実際の Claude Code が、中継の渡す設定（`defaultMode: default` など）で承認を求め、答え（許可・常に許可・拒否）に従うこと。MCP のツールで返信すること。実際のアダプターで再開すること。偽のエージェントでは代われず、安全境界に関わります。
- **モデルの能力。** 画像の色を答える、正しいルームの画像を返す、別のルームに投稿する、記録から停止中の依頼を探す。失敗しても、中継の退行かどうかを見分けられません。0.1.1 の作業では、Haiku で画像の手順が 3 回とも失敗しました。

**判定**

`line.sh` は、中継が起動しなかったときのほかは、手順が失敗しても終了コード 0 で終わっていました。0.1.1 の作業の 1 回目は、常に許可を確かめられていなかったのに 0 でした。

## 決めたこと

- **中核。** `test/e2e/line.sh claude`（ペアリング、返信、承認の許可・常に許可・拒否）と `test/e2e/resume.sh claude` を、e2e の中核とする。モデルの能力に頼る手順は、`--full` を付けたときだけ走らせる。消さない。画像を待つ時間は 2 分までにする。
- **判定。** 各スクリプトが、手順ごとに、作業ディレクトリのファイル、送信の記録、中継のログで判定し、1 つでも失敗すれば 0 以外で終わる。失敗しても次の手順に進み、最後に失敗した手順を挙げる。`--full` の手順の失敗も失敗とし、モデルの能力に頼る手順であることを示す。共通の部分は `test/e2e/lib.sh` に置く。
- **契機。** 走らせるかは、本人の判定ではなく、`scripts/e2e-targets.ts` が `main` との差分から出す。`bun run mutation` が、変異の前に表示する。（追記 2026-11-20）`bun run pre-pr` は、PR 本文の下書きに、挙げた e2e ごとの結果の欄を作る（ADR 0025）。中核を挙げるのは、次を変えたとき。
  - `src/harness/`、`src/core/mcp.ts`、`src/prompt.ts`、起動まわり（`src/main.ts`、`src/workspace.ts`、`src/home.ts`、`src/serve-args.ts`、`bin/`）、`test/e2e/`。
  - ハーネスのアダプターと ACP・MCP の SDK のバージョン（`package.json` と `bun.lock` の差分）。
  - コネクターと `src/core/relay.ts` は、単体テストで守るので、契機にしない。
- **リリースの前の関門。** バージョンを上げる PR の前に、中核を走らせる（`docs/releasing.md`）。Claude Code は固定していないので、ほかに変更がなくても、利用者の環境で結合が壊れることがあり、それを拾う。モデルは Haiku で足りる。
- **Chatwork の e2e**（`test/e2e/chatwork.sh`）は、中核の外とする。判定と `--full` は、中核と揃える。自身を変えたときだけ挙げる。ほかのチャットサービスの扱いは、順に決める。
- **CI では走らせない。** ログインした Claude Code の利用枠を使うので、CI で走らせるには、API のキーを secret に置き、API の料金を払う必要がある。
- ミューテーションテストの判断（ADR 0021）は変えない。`bun run mutation` に、ファイルを渡せるようにする（差分の行ではなく、そのファイル全体を変異させる）。

## 見直す条件

- 中核の手順で、中継の退行ではない失敗（モデルやアダプターの揺れ）が続いたとき。
- 契機に挙げないパスの変更で、e2e でしか見つからない不具合が出たとき。パスを足す。
- 中核が十分に短くなり、CI での定期実行の費用が見合うと分かったとき。
- ほかのハーネス（OpenCode など）に正式に対応するとき。中核をハーネスごとに決める。

## Considered Options

- **文章の規則で、契機を決める。** 「〇〇を変えたら e2e を走らせる」。該当するかを本人が判定するので、ADR 0021 で外した形と同じで、漏れる。
- **CI で、変更したパスから e2e を走らせる。** 一般的な形だが、上のとおり、API のキーと料金が必要になる。
- **定期実行。** 同じ理由で見送る。
- **`src/` のすべてを契機にする。** 漏れはないが、ほとんどの PR で e2e を走らせることになり、速くならない。
- **画像や別のルームへの投稿の手順を消す。** モデルや Claude Code の更新で、どこまでできるかを確かめる手段がなくなる。選んで走らせる形で残す。

## Consequences

- e2e の判定が通ることは、モデルの返事の中身まで正しい証拠ではありません。判定するのは、ファイル、記録、ログに現れることだけです。
- `scripts/e2e-targets.ts` が何も挙げないことは、e2e が不要な証拠ではありません。パスの一覧は、ハーネスとの結合が今どこにあるかに依存します。結合を別のファイルに移したら、一覧も直します。

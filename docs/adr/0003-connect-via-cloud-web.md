# アダプターは Bridge ではなく、標準 platform の cloud_web で cc-connect に接続する

> ADR 0006 で cc-connect の利用をやめ、自作の中核が ACP でハーネスを動かす構成に置き換えました。

ADR 0001 で決めた自作アダプターについて、cc-connect との接続方式を変更します。Bridge をやめ、cc-connect 1.5.0 で追加された標準 platform の cloud_web（CWIP v1）を使います。cloud_web では、cc-connect がアダプターの WebSocket に接続してきます。アダプターは中継サーバーとして、サービス固有の部分だけを担当します。具体的には、受信と署名の検証、メンションの抽出、送信です。

Bridge は標準 platform ではないため、ADR 0001 に書いた次の制約があります。標準 platform である cloud_web には、これらの制約がありません。

- 別の標準 platform を 1 つ用意しないと起動しない。上流の issue #1438・#1516 は未解決のまま。
- エンドポイントがすべてのネットワークインターフェースで待ち受ける。
- 送信者の許可、重複の除去、メンションの判定のいずれもない。

cloud_web には、送信者の許可（`allow_from`）、メンションがなければ反応しない設定（`group_reply_all = false`）、`msg_id` による重複の除去、再接続と ping の仕組みがあります。2026-11-07 に、ローカルで次のことを確認しました。

- cloud_web だけで起動できた。アダプターがあとから起動しても接続できた。
- メンションのない発言と、許可していない送信者の発言を無視した。
- 同じ `msg_id` のメッセージは 1 回だけ処理した。
- `share_session_in_channel = true` で、セッションがルーム単位になった。
- `name` の異なる cloud_web を 2 つ並べると、セッションが分かれた。
- テキストでの実行承認が機能した。

## Considered Options

- Bridge のまま進める。上流での実績は cloud_web より長い（cloud_web は追加以降、IPv6 のテスト修正が 1 件あるだけ）。ただし、上に挙げた制約を回避するコードを、アダプター側で持ち続けることになる。

## Consequences

Bridge では実現できて、cloud_web では実現できないこと：

- 1 本の接続で、メッセージごとに複数のプロジェクトに振り分けること。cloud_web の platform は 1 つのプロジェクトに属します。プロジェクトごとに cloud_web を用意し、アダプターが複数の接続を受け付ければ、同じことができます。
- Bridge の REST API によるセッション管理（`/bridge/sessions`）。ルームでの `/new`・`/list`・`/switch` か、cc-connect の管理 API で代替できます。
- cc-connect の再起動直後に、ルームへ能動的に送信すること（cron・timer・`cc-connect send`）。cloud_web は返信先をメモリ上にだけ保持するので、再起動後は、そのルームから 1 通届くまで送信できません。アダプター側では回避できません。現在の要件にはなく、cron なども無効にしています。必要になったら本体に PR を出します。
- 動画の送信。cloud_web はファイルの送信に切り替えます。LINE での動画の送信は要件にありません。
- コマンド一覧のスナップショットと、進捗表示の形式の通知（Bridge の metadata）。表示モードは quiet で、出力はテキストだけなので使いません。
- 再接続の間隔をアダプター側で決めること。cloud_web では cc-connect が再接続し、待ち時間は 2 秒から 30 秒まで倍々に延び、接続に成功しても元に戻りません（実測で約 30 秒）。そのため、アダプターの再起動中に返信が失われることがあります。返信が失われた可能性をルームに知らせる処理で補います。

アダプター側で守ること：

- `register_ack` では `capabilities` を必ず明示します。省略すると、cc-connect はすべての機能に対応しているものとして扱います。
- トークンは URL のクエリにも含まれるので、リクエストの URL をログに出力しません。
- cc-connect が重複を除去するのは 60 秒間だけです。LINE の再送に備えて、`webhookEventId` でも重複を除去します。
- 返信が失われるケースは、Bridge と同様に残ります。切断中の送信は失われ、cc-connect はエラーを記録するだけです。
